# 公部門開源軟體應用參考手冊

數位發展部（moda）｜V2.2（114.12.24）｜全文 89 頁

## 為什麼有這本手冊

**公部門的痛點**：資訊人手有限、技術創新慢、被單一廠商綁定

**手冊的核心主張**：

- 專有軟體模式 → 機關只取得「**使用權**」，轉換成本高
- 開源軟體模式 → 機關取得「**所有權**」，降低授權成本、避免 vendor lock-in
- 進一步推動「**公共程式（Public Code）**」：公帑開發的系統，以開源授權釋出，取之公共、用之公眾

> 對象：機關資訊規劃人員、專案承辦、IT 開發與維運人員

## 第一章｜開源軟體的起源

- 1950–70 年代：原始碼共享是常態（UNIX 早期隨原始碼釋出）
- 軟體商業化後，廠商開始封閉原始碼
- 1983：Richard Stallman 因 Xerox 印表機驅動程式拿不到原始碼，發起 **GNU 計畫**，提出自由軟體四大自由與 **GPL**
- 1997：Eric Raymond《大教堂與市集》——
  > given enough eyeballs, all bugs are shallow
- 1998：Netscape 開源（→ Firefox），**OSI** 成立，定義 **OSD（開放原始碼定義）**

**重點**：只有採用 OSI 認可授權條款的軟體，才叫開源軟體。單純公開原始碼 ≠ 開源。

## 開源已是現代數位基礎

| 領域 | 開源專案 | 市佔/地位 |
|---|---|---|
| 伺服器 OS | Linux | 58.4%（Windows 僅 10%，W3Techs 2025/11） |
| Web server | Apache + Nginx | 合計 58.2% |
| 前端 / 跨平台 | WebKit、React、Vue、Angular、**Flutter（Google, BSD-3）** | 行動 app 的 UI 層也是開源天下 |
| 雲端 | Docker、Kubernetes | Apache 2.0，AWS/GCP/Azure 全支援 |
| AI | PyTorch、TensorFlow、NumPy | 深度學習基礎 |

## 國際趨勢（1）：德國 openDesk

- **ZenDiS**（數位主權中心，2022 成立）的旗艦產品
- 整合多個成熟開源軟體（基礎含 Nextcloud）成公部門辦公協作平臺
- 文書、郵件、行事曆、視訊、專案管理、Wiki 一站式

**意義**：
1. 減少 vendor lock-in（開放原始碼 + 開放標準）
2. 提升透明度與安全性（可被第三方審核）
3. 統一標準化，降低訓練與維護成本
4. 落實「數位主權」政策

## 國際趨勢（2）：聯合國與美國

**聯合國（2020）**：《秘書長數位合作路線圖》提出「數位公共財」
五大類型：開放資料、開源軟體、開放內容、開放標準、開放 AI 模型

**美國（2016）**：OMB《聯邦程式碼政策》（Federal Source Code Policy）
- 跨部門流通採購的客製化程式碼
- 部分成果對民間開放釋出

**民間倡議**：Public Money, Public Code

## 授權條款光譜：嚴謹 → 寬鬆

| 授權 | 強度 | 核心義務 |
|---|---|---|
| **AGPL** | 最嚴 | 連網路服務也須公開完整原始碼 |
| **GPL** | 嚴 | 修改、整合、合併皆須以 GPL 開源（感染性） |
| **LGPL** | 中 | 僅透過函式庫介面使用可不開源 |
| **MPL v2** | 弱 copyleft | 只有「被修改的檔案」須開源（檔案層級） |
| **Apache 2.0** | 寬鬆 | 保留聲明 + 貢獻者授予專利權 |
| **MIT** | 寬鬆 | 僅須保留著作權與授權聲明 |
| **BSD-3-Clause** | 寬鬆 | 保留聲明 + 不得用原作者名背書衍生品（Flutter 採用） |
| **Boost 1.0** | 更寬鬆 | 二進位散布不強制附聲明 |
| **Unlicense** | 無 | 直接釋入 public domain |

## 授權條款：實務判斷重點

- **GPL 的「感染性」**：把 GPL 程式碼整合進專案 → 整個衍生作品須採 GPL
  - 例外：只當外部工具或透過標準介面使用
- **AGPL 補洞**：SaaS 不散布程式也算，網路服務須開源
- **Apache 2.0 vs MIT**：Apache 多了明確的專利授權，大型基礎設施（Hadoop、K8s）偏好它
- **雙重授權（Dual License）**：同一軟體同時提供開源版與商業版

> OSI 認可授權超過 120 種——選型可參考 Choose an Open-Source License

## 第二章｜開源 vs 專有軟體

| 面向 | 專有軟體 | 開源軟體 |
|---|---|---|
| 財務成本 | 授權費 + 技術服務費 | 以技術服務費為主 |
| 程式碼透明度 | 不公開，廠商維護 | 公開，社群共同檢視 |
| 漏洞修補 | 廠商排程 | 社群監督強、更新頻繁 |
| 供應商 | 單一原廠/代理商 | 可一至多家，選商限制少 |
| 系統整合 | 取決於產品 API | 開放標準，整合彈性大 |
| 授權管理 | 專屬授權、禁止逆向 | 多種授權並存，須查相容性 |

## 開源軟體六大效益

1. **財務成本可預期**：免授權費，維護費具議價能力
2. **安全管理自主性高**：原始碼公開，社群可及早發現漏洞
3. **高度客製化**：可自由修改，貼合業務流程
4. **高度系統整合力**：標準協定與格式，跨平臺
5. **合作廠商選擇彈性**：不被單一供應商鎖定
6. **政策與公共價值**：透明、可審查，增進公民信任

## 開源軟體五大風險

1. **轉型風險**：資料遷移、流程再設計、教育訓練等隱性成本
2. **廠商品質與維護責任**：缺乏可靠維護團隊將影響業務運作
3. **資安風險**：須建立監控機制即時修補（Red Hat 2022：89% IT 領導者認為開源與專有一樣安全）
4. **授權與法律風險**：授權條款具法律效力，相容性處理不當即侵權
5. **使用者接受度**：習慣 Microsoft Office / Google Workspace，教育訓練與文化轉變是關鍵

## 三種導入模式

| 模式 | 適用情境 | 案例 |
|---|---|---|
| **應用 Adopt** | 需求可直接對應成熟開源專案 | 直接導入，效率高、風險低 |
| **整合 Integrate** | 組合多個開源專案成在地化方案 | 德國 openDesk（歐洲主流模式） |
| **自主開發 Self-built** | 法規/特殊流程/國安、數位主權 | 數位身分、AI 模型、資安基礎設施 |

**成功關鍵：Open First（開放優先）**
- 專案初期即預設未來將開源
- 開放是常態，封閉是經過評估的例外
- 參考英國 GDS：「安全應該設計在開放中，而不是封閉中」

## 缺乏開源治理的三大風險

| 風險 | 說明 |
|---|---|
| **供應鏈盲點** | 廠商未揭露使用的開源套件，上游爆漏洞時下游無法應變 |
| **版本與維運風險** | 不同系統用同一元件的不同版本，長期維運衝突 |
| **授權風險** | 未遵循授權義務 → 法律糾紛，或被迫公開整個系統 |

**解法**：制定「開源軟體政策」（Open Source Software Policy）
- 不需立法，可從單一專案的規範共識做起，逐步擴及機關
- 涵蓋「探索、使用、貢獻、釋出」四個面向

## SBOM：開源治理的第一步

**軟體物料清單（Software Bill of Materials）**——建議最先導入的管理工具

> SBOM 不是終點，是起點：它是「動態的、機器可讀的」資產清單

| 功能 | 應用 |
|---|---|
| 漏洞管理 | 自動比對元件與 CVE 資料庫，即時預警 |
| 授權合規 | 程式化分析授權類型與義務 |
| 供應鏈透明化 | 清晰可驗證的依賴關係圖 |

## SBOM 格式：SPDX vs CycloneDX

| 特性 | SPDX | CycloneDX |
|---|---|---|
| 主導組織 | Linux 基金會 | OWASP 基金會 |
| 初始核心 | 授權合規與法律 | 漏洞管理與資安 |
| 優勢 | 授權描述精確、檔案層級詳盡 | 輕量、自動化導向、漏洞參考（VEX） |
| 適用 | 採購與法務審查 | DevSecOps / CI/CD 流程 |

**成熟組織的做法**：合約要求廠商交 SPDX，內部 CI/CD 自動產生並分析 CycloneDX

## OSPO 與國際標竿案例

**OSPO（Open Source Program Office）**：協調開源事務、執行規範、教育訓練、社群窗口
- 2025 年全球網絡 **FLOSS-PSO** 成立，串連各國公部門 OSPO

| 案例 | 重點 |
|---|---|
| 台灣企業案例 | KKCompany 在 OCF 協助下取得 OpenChain ISO/IEC 5230 第三方認證 |
| 美國 CISA | 開源視為關鍵基礎設施，聚焦安全與風險管理 |
| 美國 CMS | 成立 OSPO，開發 repo 模板與成熟度模型 |
| 臺北市資訊局 | 臺北城市通開源釋出，合約預先約定開源治理規則 |

## OpenChain 國際標準

由 Linux 基金會推動，定義「What & Why」而非「How」，可由小而大循序導入

**ISO/IEC 5230（授權合規）**——處理法律風險
- 計畫基礎：成文政策、角色職責、教育訓練
- 管理支援：資源配置、法務支援、外部溝通管道
- 流程實踐：元件追蹤（SBOM）、授權審查、合規產物管理
- 社群參與：貢獻政策

**ISO/IEC 18974（安全保障）**——處理資安風險
- 漏洞偵測（掃描 SBOM 比對 CVE）、風險應對、持續監控
- 外部通報管道、內部應變流程、客戶溝通

**認證路徑**：免費線上自我認證，或第三方稽核認證

## 第三章｜需求與設計階段

1. **需求釐清**：確認業務目標、檢視法規與資安限制
2. **模組化需求**：切分為可獨立開發、可替換的模組，取代過度設計
   - 案例：英國 NHS Digital 以開放 API 標準讓供應商模組化界接
3. **盤點現有開源專案**：檢視社群活躍度、維護頻率、授權條款
4. **元件選用三大檢核**：
   - **授權相容性**（注意 GPL 感染性）
   - **安全狀況**（已知 CVE、安全更新紀錄）
   - **社群健康度**（活躍維護者、友善氛圍）
   - *對 Flutter 開發者：這三點剛好對應 pub.dev 的 LICENSE、是否有 CVE/仍在維護、Likes/Popularity 與最近更新*
5. **風險分析**：威脅建模、資料設計（PII 加密）在設計階段就做

## 開發與測試階段

**核心理念：Upstream First（上游優先）**
- 修改開源元件時優先思考：能否回饋上游？
- 長期維護獨立分支 → 與上游脫節 → **Fork Fatigue（分支疲勞）**，最終無法升級

**自動化治理四件事**：

| 項目 | 做法 |
|---|---|
| 版本控制 | Git + 清晰分支策略與 commit 規範 |
| SBOM × CI/CD | 每次 build 自動產生並檢查 SBOM |
| 自動化合規檢核 | 授權掃描、合規檢查、漏洞掃描 |
| 漏洞修補紀錄 | 標準化流程 + 詳實追蹤歷史 |

<small>*落地工具：Flutter 用 `flutter pub deps` + cdxgen 產 SBOM、`flutter_oss_licenses` 擋 GPL；GitHub 用 Dependabot / Actions / CodeQL，repo 內直接開啟*</small>

## 上線與驗收階段

思維轉變：從「交付一個產品」到「**孵化一項公共資產**」

**驗收三核心**：
- **可轉移性**：完整技術文件——新團隊憑文件就能建環境、部署、理解架構（避免 soft lock-in）
- **可讀性**：足夠註解、一致命名、API 文件、reproducible build
- **永續性**：智財權歸屬明確（參考工程會《資訊服務採購作業指引》）

**最終交付文件包**：SBOM + 授權檢核報告 + 資安風險評估報告

**對標國際**：以「公共程式標準」（Standard for Public Code, SfPC）評估開源成熟度

## 開源釋出：維護等級分級

> 迷思：「所有開源專案都必須永遠保持活躍」——資源有限，分級才是負責任

| 等級 | 定位 | 適用 |
|---|---|---|
| **Tier 0–1** | 僅原始碼存檔（Archived） | 一次性活動網站、已結案研究工具 |
| **Tier 2** | 官方長期維護 | 報稅、數位身分、災防告警等關鍵系統 |
| **Tier 3–4** | 轉交社群託管 | 視覺化工具、設計系統等非關鍵平臺 |

公開聲明「封存」不是失敗，是清楚設定外界期望、釐清維護責任

## 社群貢獻機制

健全的開源專案 repo 應具備：

- `CONTRIBUTING.md`：如何開 issue、發 PR、編碼風格、測試要求
- `CODE_OF_CONDUCT.md`：社群行為準則
- `GOVERNANCE.md`：決策流程、維護者角色
- **公開的議題追蹤**：錯誤回報、功能建議都在公開系統進行
- **程式碼審查**：至少一位維護者 review 才能合併

**積極互動**：多元回饋管道、開源範例、Hackathon——把「使用者」轉化為「貢獻者」

## GitHub：開源協作的基礎設施

手冊雖未專章介紹，但 issue、PR、Discussions、流程圖處處是 GitHub 的慣例。它在公共程式生命週期中橫跨三層角色：

| 層 | 角色 | 對應手冊章節 |
|---|---|---|
| **託管** | 全球最大程式碼儲存庫；公共程式平台底層多為 Git/GitHub | 第二章 平台清單 |
| **協作** | Issue / PR / Code Review / Discussions | 第三章 社群貢獻機制 |
| **治理** | Dependabot、Dependency graph + **SBOM export**、Actions、CodeQL | 第二/三章 SBOM 與自動化治理 |

> 對機關的意義：很多治理要求（SBOM、漏洞掃描、合規檢查）不必另建工具，**在 repo 設定內就能開啟**，降低導入門檻

## 第四章｜維運七大工項

| 工項 | 開源實務建議 |
|---|---|
| 系統監控 | Prometheus（時序資料庫 + PromQL）+ Grafana 儀表板 |
| 日誌管理 | 集中化收集、結構化格式（JSON）、即時搜尋、合規保存 |
| 容量管理 | 模組化工具組合、Auto-scaling |
| 資安管理 | 身分驗證、權限控管、加密、IDS、弱掃 |
| 功能維護 | 透過 issue tracker 與社群協作（issue → PR → review → release） |
| 版本控管 | Git/SVN + CI（Jenkins、GitLab CI） |
| 文件管理 | 統一編號、版本標示、搭配版控與協作平臺 |

## 永續經營五大策略

1. **人才培育與文化形塑**：moda 已在「e 等公務園+」上架 8 堂公共程式課程（基礎班 101–104、進階班 201–204）
2. **社群動態追蹤與持續整合**：定期檢視安全修補與版本動態，結合自動化工具檢查相依套件
3. **系統管理與升級策略**：升級前檢查相容性，「風險可控、功能穩定」，關鍵元件（DB、認證）特別謹慎
4. **授權條款管理與再利用**：授權掃描工具（如 FOSSA）、元件審查流程、定期合規稽核
5. **連結社群與公共程式平臺**：重大開發成果回饋上游或公開於 code.gov.tw

- 提供可直接放入招標文件的條文範本

**附錄五：授權合規評估檢核表**（每個開源元件逐一盤點）
- 基本資訊 → 授權條款 → 預期用途（是否修改/連結/散布）→ 條款遵循
- 開發成果作為公共程式的五項要件檢核

**附錄二 FAQ 精選**：
- 程式碼公開 ≠ 資安問題：「安全性取決於維護機制，而非是否開源」
- 再利用公共程式的資安責任，仍由系統開發廠商負責

## 總結

**手冊的三層訊息**：

1. **概念層**：開源 = 取得所有權、技術自主、數位主權——國際公部門已是主流
2. **治理層**：政策 → SBOM → OSPO → OpenChain（ISO/IEC 5230 + 18974），風險才能被量化、追蹤、管理
3. **實務層**：Open First、模組化、Upstream First、驗收看可轉移性、釋出分維護等級

> 開源治理若能成為**制度**，而非專案，
> 才能讓公共程式真正成為全民共享的數位資產。
> ——義大利 AgID / CSI Piemonte 經驗

## 延伸題目｜AI 生成程式碼的「抄襲」問題

> 以下為手冊未涵蓋的延伸討論，AI coding 普及後浮現的新治理盲點

**問題本質**：Copilot、Cursor、Claude Code 等工具訓練於海量開源程式碼，生成內容**可能逐字重現訓練資料**，卻不附原始授權聲明。

- **授權層**：若重現的是 GPL 程式碼，等於把感染性授權悄悄帶進專案，卻沒人知道 → SBOM 與授權掃描的新盲點
- **著作權層**：美國著作權局已表態「純 AI 生成內容不受著作權保護」→ 公帑開發成果的權利歸屬出現模糊地帶
- **指標案例**：*Doe v. GitHub*（2022）控告 Copilot 移除授權聲明違反 DMCA，是業界首樁相關訴訟

**為何對公共程式特別敏感**：公共程式本來就要開源釋出、要求授權可追溯——AI 帶進來路不明的程式碼，正好打在這條紅線上。

## 延伸題目｜可採取的因應

| 面向 | 做法 |
|---|---|
| 工具設定 | 開啟 Copilot 等的**重複偵測過濾**（matching public code → block） |
| 流程 | AI 生成的程式碼一律納入既有**授權掃描 + code review**，不因「是 AI 寫的」而豁免 |
| 紀錄 | 保留 AI 使用範圍紀錄，重大模組標註是否含 AI 生成，供日後追溯 |
| 採購 | 招標文件可要求廠商揭露 AI 工具使用情形，並承諾交付物授權可追溯 |

> 核心心法不變：手冊的 **SBOM + 授權合規 + 人工審查** 三件事，正是 AI 時代最好的防線——
> 工具變了，治理原則沒變。
